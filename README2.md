# شرح المشروع بالعربية — AI Sales & Customer Automation System

## 1. ما هو المشروع؟

هذا المستودع هو أساس تقني لنظام أتمتة المبيعات وخدمة العملاء متعدد القنوات. الفكرة النهائية هي استقبال رسائل العملاء من قنوات مثل WhatsApp وTelegram وInstagram وFacebook، والاحتفاظ بسياق المحادثة، والبحث في كتالوج منتجات موثوق، وتأهيل العملاء المحتملين، ثم تحويل المحادثة إلى موظف عند الحاجة.

**الحالة الحالية مهمة:** المشروع في مرحلة تطوير مبكرة. توجد بنية API وقاعدة بيانات، ومسار فعلي لاستقبال منشورات كتالوج المنتجات من Telegram ومراجعتها عبر أوامر مشغّل Telegram. لكن النظام الكامل متعدد القنوات، والردود المدعومة بالذكاء الاصطناعي، والتشغيل التجاري الفعلي لم تكتمل بعد. نجاح CI لا يعني أن النشر الإنتاجي قد تم.

## 2. ما الذي يعمل أو أُضيف حتى الآن؟

### واجهة API
- التطبيق مبني على FastAPI ويُشغّل بواسطة Uvicorn.
- فحص الصحة متاح عبر `GET /healthz`.
- توجد واجهة عامة تجريبية `POST /v1/webhooks/{channel}` للقنوات `whatsapp` و`messenger` و`instagram` و`telegram`. هذه الواجهة تقبل غلاف حدث موحّد فقط؛ لا تحفظ الحدث ولا تنفّذ معالجة رسائل حقيقية.
- توجد مسارات مخصصة لاستقبال منشورات كتالوج Telegram وتحديثات بوت المشغّل.

### كتالوج المنتجات من Telegram
- يستقبل المسار `POST /v1/webhooks/telegram/catalog` تحديثات `channel_post` و`edited_channel_post`.
- يتحقق من ترويسة Telegram السرية، ومن ربط معرّف القناة بمعرّف المتجر (tenant).
- يحلل حقول المنشور بالعربية والإنجليزية، مثل كود المنتج، الاسم، السعر، العملة، الألوان، المقاسات، والتوفر.
- تُسجل أحداث الاستقبال مع مفتاح فريد لتقليل معالجة التحديث نفسه مرتين.
- إذا كان كود المنتج أو اسمه ناقصًا، يُحفظ المنشور في `product_review_queue` بدل إسقاطه.
- المنتجات المستخرجة تدخل بحالة `needs_review` ولا تصبح قابلة للبحث أمام العملاء قبل موافقة المسؤول.
- صور Telegram تُحفظ حاليًا كمراجع `file_id`؛ تنزيل الوسائط وتخزينها في مخزن دائم غير منفذ.

### أوامر المشغّل في Telegram
يدعم المسار `POST /v1/webhooks/telegram/operator` الأوامر التالية في المحادثة الخاصة مع البوت:
- `/help` — عرض المساعدة.
- `/product A100` — عرض منتج معتمد.
- `/search adidas` — البحث في المنتجات المعتمدة ضمن المتجر.
- `/review` — عرض المنتجات والمنشورات التي تحتاج إلى مراجعة.
- `/approve A100` — اعتماد منتج بعد استيفاء البيانات المطلوبة.
- `/reject A100 سبب الرفض` — رفض منتج مع تسجيل السبب.
- `/human <conversation_id>` و`/ai <conversation_id>` — تغيير وضع محادثة موجودة.
- `/status <conversation_id>` — الاستعلام عن وضع المحادثة.

تُقيّد أوامر الإدارة بقائمة معرفات Telegram المسموح بها، ويُربط المسؤول بمتجر محدد عبر الإعدادات. تُسجل قرارات مراجعة المنتجات في سجل تدقيق. وظائف المحادثات والتحويل إلى موظف ما زالت محدودة ببنية البيانات الحالية وليست منظومة خدمة عملاء متكاملة.

### قاعدة البيانات
توجد ترحيلات SQL مرقمة في `database/migrations/`:
- `0001_initial.sql`: المتاجر والقنوات وجهات الاتصال والمحادثات والرسائل والعملاء المحتملون.
- `0002_product_catalog.sql`: المنتجات ووسائطها وأحداث الإدخال وسجل تدقيق المشغّل.
- `0003_product_review_queue.sql`: قائمة المنشورات غير المكتملة التي تحتاج إلى مراجعة.
- `0004_product_media_deduplication.sql`: تنظيف مراجع وسائط Telegram المكررة وإضافة فهرس فريد.
- `0005_allow_telegram_channel.sql`: السماح بقناة Telegram في جدول القنوات.\n- `0006_enforce_tenant_relationships.sql`: فرض تطابق المتجر في علاقات المحادثات والقنوات وجهات الاتصال والرسائل والعملاء المحتملين عبر مفاتيح خارجية مركبة.

تستخدم قاعدة البيانات PostgreSQL. يشغّل Docker Compose خدمة `migrate` التي تنفّذ `scripts/migrate.py` قبل تشغيل API، ويُسجل المنفذ الترحيلات المطبقة في `schema_migrations` ويُفترض أن يكون تكرار التشغيل آمنًا. اختُبر ذلك على قاعدة جديدة في CI بتشغيل المنفذ مرتين والتحقق من تسجيل ست ترحيلات. يرفض المشغّل الآن تشغيل كل الترحيلات تلقائيًا إذا وجد جداول تطبيق موجودة وسجل ترحيلات فارغًا؛ يجب مراجعة المخطط وإجراء baseline مدروس بدل التخمين. راجع `docs/DATABASE_MIGRATIONS.md` لإجراءات الفحص والنسخ الاحتياطي والاستعادة. هذا لا يثبت التوافق التلقائي مع قواعد قديمة أُنشئت قبل وجود سجل الترحيلات؛ افحص المخطط وخذ نسخة احتياطية وخطّط لترحيل baseline قبل الإنتاج. الترحيل `0004` ينظف مراجع وسائط Telegram المكررة قبل إنشاء فهرس فريد، لذا راجع أثره على البيانات القائمة قبل تطبيقه.

### Docker وn8n
- يوفّر `Dockerfile` صورة لتطبيق API.
- يوفّر `docker-compose.yml` خدمات API وPostgreSQL.
- يمكن تشغيل n8n اختياريًا باستخدام ملف التعريف `automation`، والمنفذ الافتراضي مربوط بـ localhost. صورة n8n مثبتة على إصدار محدد بدل `latest`؛ راجع الإصدار دوريًا وحدّثه بعد فحص ملاحظات الإصدار والأمان.
- وجود الإعدادات في المستودع لا يثبت أن الحاويات أو تدفقات n8n قد شُغلت واختُبرت على خادم. لم يُوثق هنا نشر فعلي على خادم إنتاج.

## 3. مثال على تنسيق منشور منتج

يفضل نشر بيانات منظمة وواضحة، مثل:

```text
الكود: A100
الاسم: بجامة رياضية adidas
السعر: 1200 TRY
الألوان: الأصفر، الأبيض، الأخضر، الأحمر، الأسود، البيج، الذهبي
المقاسات: S، M، L، XL
التوفر: in_stock
```

يمكن للمحلل استنتاج بعض الحقول من المنشورات الحرة، لكن لا ينبغي الاعتماد على الاستنتاج وحده في بيانات حساسة مثل السعر أو التوفر. يبقى المنتج قيد المراجعة حتى يعتمد المسؤول السجل. مثال الألوان والمقاسات توضيحي؛ يجب إدخال القيم الحقيقية لكل منتج.

## 5. التشغيل المحلي

المتطلبات: Docker مع Docker Compose، أو Python 3.11 فأحدث لتشغيل الاختبارات محليًا.

1. انسخ ملف الإعدادات:
   ```bash
   cp .env.example .env
   ```
2. غيّر كلمات المرور والأسرار المحلية المؤقتة قبل الاستخدام، ولا ترفع ملف `.env` إلى Git.
3. لتشغيل API وقاعدة البيانات:
   ```bash
   docker compose up --build
   ```
4. للتحقق من API:
   - الصحة: `http://localhost:8000/healthz`
   - توثيق OpenAPI: `http://localhost:8000/docs`
5. لتشغيل n8n محليًا اختياريًا:
   ```bash
   docker compose --profile automation up --build
   ```
   واجهة n8n الافتراضية: `http://localhost:5678`. أكمل إعداد المالك الأول، ولا تكشف الواجهة للعامة دون HTTPS وضوابط وصول مناسبة.

لتشغيل الفحوصات من بيئة Python:

```bash
python -m pip install -e ".[dev]"
ruff check .
pytest
```

اختبارات التكامل مع PostgreSQL تحتاج إلى قاعدة اختبار وإعداد `TEST_DATABASE_URL` أو `DATABASE_URL`. يوفّر سير CI خدمة PostgreSQL للاختبارات.

## 6. إعدادات Telegram الأساسية

الإعدادات معرفة في `.env.example`، وأهمها:

- `DATABASE_URL`: رابط PostgreSQL الذي يستخدمه التطبيق.
- `TELEGRAM_CATALOG_WEBHOOK_SECRET`: السر المخصص لاستقبال كتالوج Telegram؛ ويمكن استخدام `TELEGRAM_WEBHOOK_SECRET` كبديل.
- `TELEGRAM_CATALOG_TENANTS`: ربط القناة بالمتجر بصيغة `CHANNEL_ID=TENANT_UUID`، وتفصل الروابط المتعددة بفواصل.
- `TELEGRAM_OPERATOR_WEBHOOK_SECRET`: سر مسار المشغّل؛ ويمكن استخدام السر العام كبديل.
- `TELEGRAM_ALLOWED_USER_IDS`: قائمة معرفات مسؤولي Telegram الرقمية المسموح لهم.
- `TELEGRAM_OPERATOR_TENANTS`: ربط المسؤول بالمتجر بصيغة `USER_ID=TENANT_UUID`.
- `TELEGRAM_BOT_TOKEN`: رمز البوت عند الحاجة إلى إعداد Bot API خارجيًا.

هذه الإعدادات وحدها لا تسجّل webhook لدى Telegram ولا تثبت صحة ربطه. يجب إعداد webhook الفعلي، والتحقق من عنوان HTTPS، ومعرّفات القنوات، والأسرار، وصلاحيات البوت في بيئة اختبار قبل استقبال بيانات حقيقية.

\n\n## 8. النواقص والمخاطر قبل الإنتاج

1. لم يكتمل تنفيذ تدفق المحادثات متعدد القنوات، ولا الردود الفعلية المدعومة بالذكاء الاصطناعي.
2. المسار العام `/v1/webhooks/{channel}` تجريبي وغير موثق بمصادقة مزود أو تخزين دائم.
3. يلزم اختبار إعدادات webhook الفعلية وتدفق Telegram من البداية للنهاية، بما في ذلك التعديلات والتكرار والأخطاء.
4. أضيف رفض آمن لتشغيل الترحيلات تلقائيًا على قاعدة قائمة ذات سجل فارغ، ووثيقة فحص وترحيل واستعادة؛ لكن baseline الإنتاجي الفعلي والنسخ الاحتياطي والاستعادة يجب اختبارها في staging.
5. أضيف ترحيل `0006` لفرض تطابق المتجر في علاقات القنوات والمحادثات والرسائل وجهات الاتصال والعملاء المحتملين. يجب تشغيل اختبارات تكامل عليه، كما أن هذا لا يفعّل PostgreSQL Row-Level Security.
6. أضيف حد لحجم جسم Webhook الخاص بـTelegram (256 KiB) والتحقق من بعض الحقول المتداخلة، وأزيل كلمة مرور PostgreSQL الافتراضية من إعداد Compose. ما زال يلزم إعداد HTTPS وحدود معدل الطلبات والمراقبة والتنبيه وسياسة الاحتفاظ بالبيانات.
7. صورة n8n مثبتة على `2.43.6` بدل `latest`؛ هذا تثبيت إصدار وليس ضمانًا مستمرًا للأمان. يجب مراجعة الإصدار وتحديثه وفق سياسة صيانة واضحة، ومراجعة المصادقة والتخزين والأسرار قبل الاعتماد عليه.
8. لم يُثبت في هذا المستودع أن المشروع قد نُشر على خادم أو رُبط بحسابات عملاء حقيقية.

**قاعدة الإصدار:** لا توصل حسابات العملاء الفعلية ولا تعتبر المشروع جاهزًا للبيع قبل نجاح اختبارات التكامل والنهاية إلى النهاية، ومراجعة الأمان والخصوصية، والتحقق من الاستعادة، وتجربة محدودة في بيئة staging.

## 9. الخطوات التالية المقترحة

1. مراجعة أحدث CI بعد كل تغيير.
2. تشغيل Docker Compose في بيئة اختبار نظيفة والتحقق من الصحة والاتصال بقاعدة البيانات.
3. اختبار دورة المنتج: منشور Telegram ← حفظ ومراجعة ← اعتماد/رفض ← ظهور المنتج المعتمد في البحث.
4. إكمال اختبارات تعديل المنشور، وتكرار التحديثات، وغياب السعر/العملة، وعزل المتاجر.
5. إكمال تخزين المحادثات والرسائل وسجل العملاء المحتملين، ثم ربط القنوات والذكاء الاصطناعي وn8n تدريجيًا.
6. تنفيذ مراجعة أمنية وتشغيل staging قبل أي إطلاق تجاري.

للتفاصيل الفنية، راجع `README.md` وملفات `docs/`؛ هذا الملف يشرح الحالة المنفذة والحدود الحالية بالعربية، ولا يفترض أن الميزات المخططة أصبحت جاهزة.
